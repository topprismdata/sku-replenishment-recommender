# Retail SKU Recommendation — Engineering Lessons

> Reusable engineering discipline for per-customer SKU recommendation projects
> where the metric is **F1 (or precision/recall at K)** and the data is weekly orders.
> Audience: ML engineers building similar systems in retail / FMCG / distribution.

---

## 1. Evaluation discipline (set up on Day 1)

**Time-series problems must never use random splits.**

### 1.1 Leakage 8-point checklist

| Check | What it prevents |
|---|---|
| Train period < Eval period (no overlap) | Predicting "past from future" |
| All aggregate features use train-only data | Label leaking into features via lag/rolling |
| Labels built from target period only | Same |
| Co-occurrence matrices use train only | Most common leakage source |
| Candidates generated by train-time rules | "Predict-time-unreproducible" candidates |
| N-formula inputs use train only | Subtle but real leakage |
| N-formula time-safety | ≤0.5pp gap as the last-mile guard |
| Eval customer set ⊆ train customer set | Don't pad eval with new customers |

**Wallpaper-ready checklist** (print at project start):

```
[ ] Train window strictly precedes eval window
[ ] All aggregates (co-occurrence, collab, stats) train-only
[ ] Candidate generation rule = reproducible at predict time
[ ] N formula / thresholds / quantiles inputs contain no label
[ ] Eval customer set ⊆ train-seen customers (cold-start evaluated separately)
[ ] Every "improvement" can be explained as "information from future leakage"
```

### 1.2 Walk-forward validation (instead of K-fold)

```
Train W16-W19 → Eval W20
Train W16-W20 → Eval W21
Train W16-W21 → Eval W22
Train W16-W22 → Eval W23
```

**Why not K-fold**: weekly distributions drift (e.g., W19 vs W29 customer activity
differs hugely). K-fold gives inflated F1 that doesn't generalize.

### 1.3 Compute theoretical upper bound

| Metric | What it measures |
|---|---|
| **F1-EM** | Per-customer post-hoc optimal N (business-unusable, hindsight only) |
| **Historical coverage** | Fraction of next-week purchases already in customer history |
| **Real F1** | What your model actually achieves |

**Value**: Tells the team "max possible improvement", preventing wasted effort.

## 2. Feature engineering (the core asset)

### 2.1 Successful features share one of two properties

| Property | Examples |
|---|---|
| **Cross-competition transferable** | Instacart `up_order_strike`, `reorder_ratio`, `gap` features — proven in similar problems |
| **Business-understanding derived** | Route × SKU collaboration — captures business structure that's invisible in raw data |

### 2.2 Failed features share 4 common root causes

| Failure mode | Strategy |
|---|---|
| **Feature redundancy** (corr > 0.7 with existing) | Check correlation matrix BEFORE adding |
| **Signal subset** (covered by existing features) | Venn-diagram against existing Top-20 |
| **Wrong business intuition** (e.g., "amount matters") | Validate hypothesis with EDA first |
| **Wrong objective alignment** (e.g., NDCG instead of F1) | Optimize the metric you actually evaluate |

### 2.3 The 3-step feature acceptance test

```
1. Can the business hypothesis be stated in one sentence?
2. Is the correlation with existing Top-20 features < 0.7?
3. Does it improve ≥0.2pp on at least one channel?
   All 3 yes → add. Otherwise drop.
```

### 2.4 Saturation signals (more important than individual features)

| Symptom | Meaning |
|---|---|
| 3-4 consecutive experiments with no F1 gain | Feature engineering saturating |
| New features all correlate > 0.7 with existing | Information already captured |
| Real F1 close to historical coverage | Remaining headroom is in N formula / external data |

**When to switch paradigm**: 3-4 versions with no positive return → **stop adding features, switch data / switch paradigm**.

## 3. Business understanding (often the actual bottleneck)

5 categories of business questions to ask before training:

1. **Does scale predict what to buy?** (Same-size customers overlap only ~40% in SKUs — scale ≠ SKU preference)
2. **What's the model ceiling?** (Historical coverage = upper bound; don't expect to invent SKUs)
3. **How different are sub-populations?** (If very different → split models)
4. **Is the baseline decaying?** (Don't chase an accelerating retreating car)
5. **What's the impulse vs habitual split?** (Impulse SKUs are unpredictable, don't waste features)

**Experience**: 5 well-articulated business insights are worth more than 100 features.
Recommendation system bottleneck is rarely the model — it's business understanding.

## 4. Engineering practices

### 4.1 AutoGluon as first-line baseline (lowest-cost default for small teams)

```python
from autogluon.tabular import TabularPredictor

predictor = TabularPredictor(
    label='label', problem_type='binary', eval_metric='roc_auc',
    path='ag_final', verbosity=0,
).fit(
    train_data=train_df,
    hyperparameters={
        'GBM': [{'num_leaves': 63, 'min_child_samples': 100},
                {'num_leaves': 31, 'min_child_samples': 50}],
        'CAT': {}, 'XGB': {},
        'RF': [{'criterion': 'gini'}, {'criterion': 'entropy'}], 'XT': {}
    },
    time_limit=300,
    excluded_model_types=['NN_TORCH', 'FASTAI'],  # thousands-of-rows → GBDT more stable
)
```

**Key decisions**:
- **Exclude NN_TORCH/FASTAI**: with limited data, GBDT is more stable; DL needs 5-10x more data
- **Multiple GBM configs**: lets AutoGluon do light ensembling
- **Explicit `time_limit`**: prevents runaway training

### 4.2 Per-segment independent modeling

```
channel_a (1,673 customers) ─┐
channel_b (423)              ─┼─→  4 independent models + 4 N parameter sets
channel_c (577)              ─┤
channel_d (430)              ─┘
```

**When to split**:

```
1. Do different segments have significantly different label distributions?
2. Do different segments have significantly different optimal N?
   Either yes → split.
```

### 4.3 MLflow tracking (everything reproducible)

| Tracked item | Why |
|---|---|
| Parameters | N formula (base, mult, cap), train week window — reproducibility |
| Metrics | F1 / Precision / Recall per channel per week — comparability |
| Models | Full AG model object in mlruns/ — rollback |
| Feature lists | `feat` + `cat_feat` explicit save — trace "which feature contributed X pp" |

### 4.4 Two-stage submission (training and prediction explicitly separated)

```python
# Stage 1: train, with label
model.fit(train_weeks=W16-W28, label_week=W29)

# Stage 2: predict, target-week label ignored
model.predict(feat_weeks=W17-W29, target_week=W30)
```

**Why**: At predict time, feature range ≠ train range (must include latest window).
Writing it explicitly prevents "forgot to update feat_weeks" bugs.

## 5. Reflection discipline (the highest-leverage asset)

### 5.1 Root-cause categorization of failed experiments

| Category | Example |
|---|---|
| Feature redundancy (~50%) | error analysis features, route × sub_channel |
| Wrong objective alignment (~20%) | LambdaRank (optimizes NDCG), N-predictor |
| Wrong business intuition (~20%) | amount features, box-count features |
| Signal subset (~10%) | early-bird signals |

### 5.2 "I am saturated" declaration (the most valuable sentence)

When to declare saturation (write it down, post it on the wall):

```
- 3-4 consecutive versions with no F1 gain
- New features all correlate > 0.7 with existing
- Distance to theoretical upper bound < 15pp
- Main gains come from threshold/window tuning, not new information
```

**Why this matters more than any 0.5pp optimization**: it redirects effort from
"tune harder" to "change data / change paradigm".

## 6. Reusable checklist for any similar project

1. **Evaluation first**: 8-point leakage check + walk-forward + theoretical upper bound
2. **Document business insights**: repurchase rate, ceiling, behavioral segments > 100 features
3. **Cross-competition learning**: similar problem SOTA features often transfer; don't reinvent
4. **Per-segment modeling**: when behavior differs, don't force a single model
5. **AutoGluon first**: take the default ensemble before hand-tuning
6. **Record failures**: each failed attempt with root cause is organizational memory
7. **Declare saturation**: use upper bound math to tell team "max possible gain"

---

## 7. 5 questions to ask before starting a new project

1. **What's the theoretical upper bound?** (F1-EM / R² / NDCG@K — compute and post)
2. **What's the model ceiling?** (how much of target is reproducible from history?)
3. **How different are sub-population behaviors?** (decides segmentation)
4. **What features did existing SOTA use?** (cross-competition / cross-company search)
5. **When is "saturated, stop"?** (write it down upfront to avoid wasted effort)
